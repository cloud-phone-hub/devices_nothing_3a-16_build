eMMC / UFS CID：存储芯片的“出厂身份证”
1.1 技术原理
eMMC CID（Card Identification Register） 是存储芯片内部一个 128 位只读寄存器，在芯片出厂时被一次性写入，包含制造商 ID、OEM ID、产品名、唯一序列号、生产日期等信息。CID 的核心价值在于它的唯一序列号（PSN） 字段，理论上每颗 eMMC 芯片的序列号都不同。

UFS 的情况略有不同：UFS 协议没有定义 CID 寄存器，但提供了 Device Descriptor，其中包含一个 Serial Number 字符串描述符，同样具有设备唯一性。UFS 的序列号存储在 /sys/bus/platform/drivers/ufshcd/*/string_descriptors/serial_number 路径下，文件只读。

1.2 读取方式
在 Linux/Android 内核层，eMMC CID 通过 CMD2（ALL_SEND_CID） 命令读取。在用户态，历史上可通过 sysfs 路径 cat /sys/block/mmcblk0/device/cid 获取。

关键限制：Android 7.0（Nougat）之后，/sys/block/mmcblk* 路径对普通应用完全不可读，Google 在 Android N 中显著收紧了 /sys 和 /proc 的访问权限，目的是强化应用沙箱。这意味着 CID 无法被普通 App 直接采集，只有在具有系统权限、Root 权限或通过内核态采集的场景下才可用。

1.3 为什么改机工具动不了它？
CID 寄存器是芯片出厂时一次性写入的只读区域，其前 15 字节受 CRC7 校验保护。任何对 CID 的修改若不重算 CRC，会导致 BootROM 校验失败，设备根本无法启动。即便使用非原厂工具强行改写 PSN 字段，也会制造出“物理上可读但逻辑上被 BootROM 拒认”的异常状态。改机软件、恢复出厂、刷机都无法合法修改 CID。

1.4 风控应用
在风控侧，CID/UFS 序列号可作为设备簇的锚点：同一 CID 下无论 android_id 如何变化，都归入同一物理设备。RPMB（Replay Protected Memory Block）的认证密钥甚至可以从 CID 派生，进一步提升与硬件绑定的强度。

二、传感器校准数据：物理器件的“模拟指纹”
2.1 技术原理
加速度计、陀螺仪、磁力计等 MEMS 传感器在制造过程中存在微小的物理偏差（零偏、增益误差、轴间耦合）。厂商在出厂时会为每颗传感器写入个性化的校准参数，用于补偿这些偏差。

剑桥大学的研究团队（SensorID）发现：通过分析传感器输出的原始数据，可以逆向推断出这些嵌入在固件中的工厂校准参数。校准指纹不会随时间改变，恢复出厂设置也不会重置，且无需任何特殊权限即可采集。

2.2 核心特征
SensorID 的核心特征是从传感器输出中恢复的校准增益矩阵和零偏向量。以加速度计为例，其输出可建模为：

text
output = GainMatrix × trueAcceleration + Bias + noise
通过让设备处于多个已知姿态，可以解算出 GainMatrix 和 Bias。这些参数的组合具有极高的熵值：iPhone 6S 的校准指纹约有 67 比特熵，Pixel 4/4 XL 约有 57 比特熵。这意味着在数亿台设备中，几乎不会有两台设备的校准参数完全一致。

磁力计和陀螺仪同样适用：磁力计的硬铁偏移和软铁矩阵、陀螺仪的零偏漂移曲线，都是高度设备特有的。

2.3 采集方法
研究证明，仅通过 JavaScript 或普通 App 的传感器 API 即可采集。提取过程通常不到一秒，不依赖于设备的位置或方向，在不同温度下测量也不会改变结果。这意味着风控 SDK 可以在用户无感知的情况下，在 App 启动或页面加载时完成一次校准指纹采样。

2.4 改机工具的破绽
模拟器和云手机在传感器层面的伪造最为困难：

模拟器：加速度计三轴读数在所有实例中往往恒定不变（如始终为 0.0/9.81/0.0），没有任何物理噪声，这种“完美一致性”本身就是模拟器特征。

云手机 / 多开：同一台物理主机上运行的多个虚拟实例会共享完全相同的传感器校准数据。如果风控发现 50 个账号上报的传感器校准矩阵高度一致，即可判定为同一物理设备上的多开环境。

改机工具：可以 Hook 传感器 API 返回伪造值，但伪造的校准参数无法通过多姿态一致性校验——真实设备的校准矩阵在不同姿态下应产生物理上自洽的输出，而随机伪造的值会在交叉验证中暴露矛盾。

Android 11 之后，Google 对传感器校准数据的暴露做了一定限制，但底层数据仍可通过内核或特定 HAL 路径获取，且限制并不完美。

三、电池曲线：化学特征的“动态签名”
3.1 技术原理
电池指纹与 CID 和传感器校准有本质不同：它不是出厂写入的静态参数，而是电池电化学特性的动态表现。电池的电压-电量关系曲线（充放电曲线）、内阻、老化程度等，受电池化学组成、制造批次和个体差异影响，每一块电池的充放电曲线都有细微但可测量的差异。

3.2 可采集的特征维度
Android 的 BatteryManager API 暴露了多个可用于指纹构建的字段：

充电曲线：电压随电量变化的斜率、拐点位置、恒流/恒压阶段转换点

放电曲线：不同负载下的电压下降速率

充电/放电时间：chargingTime 和 dischargingTime 的精确值

电池健康状态：通过容量衰减和内阻变化间接推断

温度-电压响应：不同温度下充放电行为的差异

研究表明，电量、充电状态和放电时间的组合可以产生超过 300 万种独特的“电池指纹”。即使电量从 67% 变为 68%，结合充电/放电状态，仍能维持 95% 以上的匹配准确率。

3.3 真实设备 vs. 设备农场的破绽
设备农场（device farm）通常会让所有手机持续连接充电器以最大化在线时间，导致这些设备的电池轨迹长期停留在 100% 电量、极少放电循环，完全缺乏真实用户的使用多样性。

风控侧的具体检测逻辑：

如果一个“新设备”上报的电池特征始终是 100% 电量 + 充电中，且长期无放电记录，标记为可疑。

如果同一账号在多个“设备”上出现电池充放电模式高度相似（相同时间的电量范围、相同的充电/放电时间比），判定为同一物理设备的重复注册。

电池曲线的老化轨迹也是强信号：真实设备的电池容量会随使用逐渐下降，而虚拟设备或重置后的设备电池老化曲线会出现不自然的“重置”（突然回到新电池状态）。

3.4 采集方式
在 Web 端，Battery Status API 曾是主要采集途径，但 Chrome 自 2020 年起逐步弃用该 API。在 App 端，Android 的 BatteryManager 和 Intent.ACTION_BATTERY_CHANGED 广播仍可提供电压、温度、电量、充电状态等原始数据，风控 SDK 可以在后台连续采样，构建充放电曲线的时间序列特征。
